# ORI scope and limitations

Day 11 reference, October 20, 2026. All operational records, readiness rules and findings are synthetic/fictional. [Metric contract](metric_contract.md), [dictionaries](data_dictionary.md), [export fields](export_dictionary.md), [reproduction instructions](reproduce.md) and [executive brief](executive_brief.md) are the supporting references.

| Area | What the prototype supports | Limit on interpretation or use |
| --- | --- | --- |
| Population and rules | Six fictional units, 300 people, eight qualifications, one staffing snapshot and 600 cases. Four configurations deliberately plant recognizable patterns. | These are not an operational sample, Navy policy, official readiness/deployability criteria or evidence of external validity. Findings identify generator behavior, not real organizational causes. |
| Time | Fixed D = October 7, 2026; current availability/unit membership; process events with an inclusive July 10–October 7 period. | Cases do not reconstruct historical staffing, qualifications or availability. This release's M/schema/reference checks are pinned; changing configuration alone does not approve another snapshot. |
| Staffing | Available / required is uncapped; local gaps are summed after each unit's shortfall is floored at zero. | Global surplus does not fill a local gap. The model supplies no skills/authority/transfer-cost/shift/demand optimization. |
| Qualification coverage | Distinct currently available/valid holders per unit/qualification; cap each pair at its requirement before summing. LEFT JOIN preserves zero-holder requirements. | One person may hold several qualifications and occupy several holder slots. Counts do not establish unique deployable people, concurrent assignments, hours or capacity. Current availability establishes neither renewal ability nor intent. |
| Expiration inventory | All currently valid certificates, including unavailable people; distinct affected people recomputed for selected cumulative 30/60/90 windows. | Certificate counts differ from people and from the eligible scenario cohort. Windows overlap and must not be added. Expiration on D is already invalid; D+N belongs to the matching expiration window. |
| No-renewal scenario | Freeze today's eligible cohort and units/staffing/availability/demand; remove certificates expiring on/before D+N. No renewals/future activations/new holders. Total/additional/new-pair gaps remain distinct. | This is conditional arithmetic, with no learned target, renewal probability or future staffing forecast. Alternative horizons repeat the baseline and cannot be summed. Operational severity or downsizing outcomes need additional explicit rules. SQL already answers the contracted scenario. |
| Administrative outcomes | Rates use eligible completed cases; open outcomes stay unknown. Selected medians are recomputed from individual eligible durations. Open age uses all cases open at D. | This supplies no service-level target, business-day calendar, case-complexity adjustment or causal explanation. The Unit F hotspot was planted. Open-only rate and empty medians are undefined, not zero performance. |
| Data quality | Python validates keys/dates/flags/FKs/counts; unresolved duplicate versions and invalid descendants are rejected. Loader blocks unapproved input and rolls back a failed transaction. | Passing configured checks is not authority to choose a duplicate record or proof that inputs reflect reality. Diagnostic accepted rows from a blocked dirty bundle are not approved analytical input. |
| Export and refresh | Each exporter verifies approved source/database records in one read-only snapshot; successful manifests gate CSV use. Python preflights hash files without writes; M checks schemas/values. | Several filesystem CSV replacements are not one atomic transaction. A successful manifest is written after replacement; interruption/failure blocks authorization. M does not hash; keep inputs stable between preflight and refresh. Desktop can retain cached visuals after a failed refresh. |
| Reproduction and evidence | Prior Linux/Windows 72-test results and accepted user-operated report checks are recorded. Day 11 runs twelve focused existing tests and three preflights. | These do not execute M/DAX or Desktop in the assistant environment. Exact installed definitions/type metadata and actual PBIX remain uninspected. Day 12 fresh-checkout execution, timed rehearsals and offline demo/backup are not established by the Day 11 runbook. |
| Distribution and release | Git carries code, SQL, M/DAX, tests and text documentation. Generated data/database, environments, private history and report binaries remain excluded. | A Git clone has no populated data or PBIX. Full Desktop reproduction needs the published build instructions or a separate user-controlled comparison report. No cloud deployment, production maintenance, real impact or full MVP release pass is claimed. |

The five [recommended reviews](executive_brief.md#five-proposed-reviews) cite observed simulated evidence and their own unproven assumptions. They are discussion prompts, not implemented interventions or an official priority ranking. Scope/date/priority changes require the user's existing master-chat decision process; none is made by this document.
